# Android permissions — what the release binary actually asks for

Read out of the built APK with `aapt2 dump permissions`, not from the source
manifest. The two can differ: a library's manifest is merged into the app's, and
a permission a dependency declared is a permission the app requests, whatever
the app's own file says.

Regenerate with:

```bash
$ANDROID_HOME/build-tools/36.0.0/aapt2 dump permissions \
  apps/mobile/android/app/build/outputs/apk/release/app-release.apk
```

## Declared

| Permission | Protection level | Why it is here | Is the user prompted? |
| --- | --- | --- | --- |
| `android.permission.INTERNET` | normal | Capacitor serves the bundled app to the WebView over an internal `https://localhost` origin. **No feature makes a network request** — see `network-audit` in the release validation report. | No. Normal permissions are granted at install. |
| `android.permission.POST_NOTIFICATIONS` | dangerous | The optional daily study reminder, and nothing else. | Yes — and only at the moment the learner switches the reminder on in Settings and picks a time. Never at launch, never on opening Settings. See `apps/web/src/native/reminder.ts`. |
| `android.permission.VIBRATE` | normal | Haptics on a correct or incorrect answer. Declared by `@capacitor/haptics`. | No. |
| `android.permission.RECEIVE_BOOT_COMPLETED` | normal | Re-registers the daily reminder after the phone restarts. Android drops pending alarms on reboot, so without this the reminder silently stops the first time the learner turns their phone off. | No. |
| `android.permission.WAKE_LOCK` | normal | Delivers the reminder on a sleeping device. Held for the moment the notification is posted and no longer. | No. |
| `${applicationId}.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` | signature | Generated by AndroidX for its own internal broadcast receivers. It is scoped to this app's signature and grants nothing to anything else. | No. |

## Deliberately absent

Location, contacts, microphone, camera, phone, SMS, calendar, call log, body
sensors, `READ_EXTERNAL_STORAGE`, `WRITE_EXTERNAL_STORAGE`, `USE_BIOMETRIC`,
`READ_MEDIA_*`, `QUERY_ALL_PACKAGES`, `SCHEDULE_EXACT_ALARM`,
`REQUEST_INSTALL_PACKAGES`, `SYSTEM_ALERT_WINDOW`, `FOREGROUND_SERVICE`.

Two of those are worth stating explicitly because a plausible implementation
would have needed them and this one does not:

* **No storage permission.** The app reads and writes nothing outside its own
  container. The one path that ever came close — exporting the learner's
  progress to a file — used the app's own cache directory and the system share
  sheet rather than shared storage, and has since been removed from the product
  along with the two plugins that served it.
* **No `USE_BIOMETRIC`.** The learner's progress is in an app-private SQLite
  database written by a plugin in this repository. The obvious off-the-shelf
  alternative, `@capacitor-community/sqlite`, pulls in `androidx.biometric` and
  SQLCipher and would have added this permission to a Hangul app.

## No exact alarms — and the permission is actively removed

`@capacitor/local-notifications` **declares `SCHEDULE_EXACT_ALARM` in its own
manifest**, and the first release build of this cycle therefore shipped it. That
was caught by reading the permissions out of the built APK, which is the reason
this audit is done that way round.

It is now removed at the manifest merger:

```xml
<uses-permission
    android:name="android.permission.SCHEDULE_EXACT_ALARM"
    tools:node="remove" />
```

Removing it is safe, and that was checked in the plugin's source rather than
assumed. The plugin only takes the exact-alarm path when a notification is
flagged as exact *and* the app can schedule exact alarms; this app flags nothing
as exact, so `LocalNotificationManager` falls through to `AlarmManager.set()`,
which is inexact and needs no permission.

`SCHEDULE_EXACT_ALARM` is a restricted permission that Play grants to
alarm-clock and calendar apps and asks everyone else to justify. "A study
reminder that arrives at 19:00 rather than at 19:00:00" is not a justification,
and shipping it would have been a policy question asked of a reviewer for no
benefit.

`scripts/audit-release-security.mjs` now fails the build if it reappears in a
packaged APK, so a plugin upgrade cannot quietly put it back.
